# PR #28 问题说明：聊天标题被当成客户消息

## 1. 问题概括

微信窗口顶部的当前会话标题可能被 OCR 解析成一条普通文字记录，并被系统误认为是客户发来的消息。

例如当前打开的会话是“许聪”，OCR 可能得到如下记录：

```json
{
  "content": "许聪",
  "sender": "customer",
  "type": "text",
  "bubble_rect": {"left": 430, "top": 112, "right": 476, "bottom": 136}
}
```

这条记录实际属于窗口标题栏，不属于聊天内容，但旧的客户消息候选判断没有将它排除。

## 2. 影响链路

错误记录进入客户消息链路后，可能发生以下问题：

1. 标题行被加入 capture 批次。
2. 调度器把它登记为待处理客户消息。
3. Brain 收到错误输入，可能产生无关回复。
4. 回复任务会改变当前会话状态、freshness 和消息锚点。
5. 由于错误消息被视为新输入，可能造成重复处理、错误点击、错误回复或阻塞同一会话后续消息。
6. 多会话运行时，错误状态还可能拖慢其他会话的扫描和调度。

因此，这不是单纯的 OCR 文本清洗问题，而是“窗口界面元数据”和“客户消息”之间的边界缺失问题。

## 3. PR #28 的实际情况

PR #28 涉及标题相关能力，但没有完成消息链路闭环。

PR 中已有的内容包括：

- 侧边栏会话名称解析；
- 当前会话标题确认；
- `active_title_region_fingerprint` 等目标确认数据；
- `bubble_rect` 等 OCR 几何信息保留。

PR 中缺少的关键能力是：

- 在客户消息候选入口判断 OCR 行是否属于窗口标题；
- 在 scheduler capture 入口再次拒绝标题元数据；
- 保证同名的真实聊天气泡仍然可以正常进入 Brain。

对 PR head `2120f16744aebe3d8edbdf9c3f407375bfeed279` 及其父版本进行检查，均未发现完整的“标题行不可作为客户消息”过滤闭环。因此目前不能简单认定这是 PR 新引入的逻辑错误，更准确的结论是：PR 延续并暴露了原有的边界缺口。

## 4. 根因

### 4.1 数据层没有区分两种文本

OCR 输出同时包含：

- 窗口标题、侧边栏名称、时间等界面元数据；
- 客户真正发送的聊天气泡。

但两者都可能被表示为 `type=text`，甚至都可能带有 `sender=customer`，仅依赖消息类型和 sender 无法区分。

### 4.2 候选过滤只覆盖了其他噪声

原有过滤主要处理：

- 自己发送的消息；
- 图片或媒体 OCR 文本；
- 非文本消息；
- 机器人回复回显。

没有处理“标题文本恰好等于当前会话名称，并且位于顶部标题区域”的情况。

### 4.3 标题识别和消息筛选是两条断开的链路

PR 能够使用标题确认当前目标，但标题确认结果没有反向用于消息候选过滤。于是系统知道“这是当前会话标题”，却仍然可能把同一行文字当成客户消息。

## 5. 推荐修复方案

本问题的责任边界就在 PR 的 OCR 消息解析和消息封装链路内，因此推荐直接修改 PR 相关代码，把标题识别和客户消息边界在源头修好，不再额外挂一层临时补丁。

修复应以最新 PR 分支为基础，由 PR 作者在其负责的 OCR/消息模块中落地，并重新提交一版 PR。

### 5.1 在 PR 的消息规范化层增加统一判断

在 PR 负责的消息规范化/封装位置增加一个中性的内部判断函数，职责只有一个：判断 OCR 记录是否为捕获元数据，而不是客户消息。

建议优先放在 `wechat_message_envelope.py` 的统一消息封装路径，并由 PR 的 OCR 文本规范化路径提供必要的区域和角色证据。这样所有上游调用者拿到的消息记录从源头就是正确的，避免在多个业务入口重复补丁。

判断顺序建议如下：

1. 读取 OCR/RPA 来源。
2. 优先识别显式区域标记，例如 `active_title`、`chat_title`、`header_only`。
3. 没有显式标记时，比较文本与当前已确认会话名称是否完全一致。
4. 检查 `bubble_rect` 是否位于聊天窗口顶部标题带，且尺寸符合标题行特征。
5. 只有同时满足“文本等于当前会话名称”和“位于标题区域”时，才判定为标题元数据。

不要使用联系人名、车型名、账号名或其他业务关键词做判断。

### 5.2 在 PR 的共享候选入口调用

修复后的 PR 消息入口必须同时保证：

- 普通工作流的客户消息候选入口；
- scheduler 的 capture 入口。

如果这两个入口无法共用同一层规范化结果，则在两个入口都调用同一个 PR 内部判断函数，不能分别实现两套相似规则。这样即使某条路径绕过了前一层，标题也不会进入 Brain 输入。

### 5.3 保留同名真实消息

不能简单地按“内容等于联系人名称”删除。以下记录必须保留：

- 内容等于联系人名称；
- 但位于正常聊天气泡区域；
- 不是窗口标题区域；
- 或者有明确的消息气泡身份和时间。

这保证客户真的发送“许聪”这类内容时不会被误删。

### 5.4 失败时采用保守策略

如果来源不是 OCR/RPA，或缺少标题所需几何信息，不应仅凭文字相等就删除消息。

只有在来源、文本和几何证据足够时才过滤；证据不足时保留记录，交给后续消息边界和 Brain 处理，避免误删真实客户消息。

## 6. 必须补充的测试

至少增加以下回归测试：

1. 当前标题行不能形成客户消息或 Brain 任务。
2. 同名文本位于正常聊天气泡区域时必须保留。
3. 显式 `active_title` 标记必须被过滤。
4. 标题行没有 sender 信息时仍能被过滤。
5. 非 OCR 来源的同名普通消息不能被误过滤。
6. 标题过滤不能改变 session key。
7. 标题过滤不能影响其他会话扫描。
8. 标题出现、真实客户消息紧随其后时，只处理真实客户消息。
9. 多会话场景不能把 A 会话标题当成 B 会话消息。
10. 过滤后 Brain、reply ledger 和发送目标的外部字段保持不变。

## 7. 当前代码状态说明

当前工作区已经在 `wechat_message_envelope.py` 验证了标题元数据过滤所需的判断条件。该文件正是 PR 负责的消息封装文件，因此这部分验证结果可以作为 PR 正式修复的基础，不需要再迁移成外挂补丁。

同事重新提交 PR 时，应把这套判断整合进最新 PR 的 OCR 规范化和消息候选链路，并删除重复的外围临时判断。最终应以 PR 自身输出的消息记录已经正确区分“标题元数据”和“客户消息”为验收标准。

## 8. PR 修改后的验收顺序

1. 先在 PR 分支修改 OCR 消息封装和规范化逻辑。
2. 用标题行、同名真实气泡、无 sender 标题行三类样本回放。
3. 运行 PR 的 OCR/Window Action 测试。
4. 运行 scheduler、工作流和多会话回归测试。
5. 检查标题不会形成 Brain 任务，也不会改变 session key、reply ledger 或发送目标。
6. 再进行真实微信桌面测试，确认连续消息和多会话扫描不受影响。

本问题涉及客户消息边界和外部契约，必须同时遵守：

- [`customer_visible_reply_ownership_baseline.md`](customer_visible_reply_ownership_baseline.md)
- [`customer_service_external_contract_and_optional_plugin_baseline.md`](customer_service_external_contract_and_optional_plugin_baseline.md)
