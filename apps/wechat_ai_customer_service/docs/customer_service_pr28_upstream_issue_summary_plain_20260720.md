# PR #28 问题概括版

给 PR 作者的简明说明。
PR：`Improve WeChat C2 OCR monitoring`
PR head：`2120f16744aebe3d8edbdf9c3f407375bfeed279`

本文不讨论业务话术，也不要求修改 Brain。只说明 PR 合并后暴露的 OCR、会话识别和微信操作问题。

必须同时遵守：

- [客户可见回复所有权基线](customer_visible_reply_ownership_baseline.md)
- [客户服务外部合同与可选插件基线](customer_service_external_contract_and_optional_plugin_baseline.md)

## 一句话结论

合并前版本已经修好了一部分群聊和会话识别问题，但 PR 合并时把这些修复覆盖掉了。结果是：微信看起来已经读了消息，但程序没有真正读到消息，所以 Brain 根本没有机会回复。

## 最直接的故障：群聊消息被读错

实测会话标题是：

```text
新数据测试(2)
```

这实际是一个群聊。里面有：

- 许聪发的一张图片；
- “这个车，我记得你们有个老款的，还在吗？”；
- “在？”。

但是 PR 版本做了下面几件错误的事：

1. 只看“新数据测试”这个名字，把它当成私聊；
2. 没有利用标题里的 `(2)` 判断这是群聊；
3. 把“许聪”这种群成员名字当成了消息；
4. 没有把群成员名字和下面的文字、图片绑定起来。

最后程序得到的是“没有有效消息”，而不是实际的文字和图片。

程序随后连续尝试了三次，仍然得到空结果，于是结束这条任务。微信因为被打开而显示已读，但 Brain 没收到消息，所以用户看到的就是“已读不回”。

### 合并前是什么情况

合并前版本已经有通用处理：

- 看到聊天标题中的成员数，就把会话修正为群聊；
- 把群成员名字当作元数据；
- 只把真正的文字、图片或语音作为消息内容。

这部分是本次合并后明确回归的功能。

## 其他已经发现的问题

### 1. 会话类型变化会导致同一个会话被拒绝

侧栏可能先认为会话是私聊，打开聊天窗口后才发现是群聊。这个变化只应该修正“会话类型”，不应该让同一个会话变成另一个会话。

但 PR 把 `conversation_type` 也当成了身份的一部分。于是：

- 会话 key 明明相同；
- 聊天标题明明相同；
- Brain 也已经生成了回复；
- 最后却因为 `private/group` 不一致而不发送。

合并前版本已经专门避免了这个问题，PR 合并后又出现了。

### 2. 已经打开正确会话，程序还会再次点击

PR 在已经知道目标类型时，仍可能重新寻找并点击侧栏行。

这会造成：

- 聊天窗口被隐藏；
- 聊天焦点丢失；
- 点击到了错误的会话；
- 后续消息捕获失败。

合并前版本已经有“当前会话正确就不再点击”的保护，合并后被覆盖。

### 3. 侧栏增强 OCR 可能把数字角标当成会话

PR 新增了一轮侧栏放大 OCR。它可能把下面这些东西误当成会话标题：

- 未读数字；
- 时间；
- 头像旁边的文字；
- 被截断的预览；
- 同一行重复识别出的文字。

这样会产生一个看起来像真实会话、实际上不是会话的候选，后续可能被错误点击。

这套增强 OCR 在合并前版本没有，属于 PR 新增的风险。

不能用“排除 2、3、纯数字”这种办法修，因为下一个界面可能出现别的数字。应该根据完整的侧栏行结构判断。

### 4. PR 里还留着旧的图片处理入口

当前系统已经有独立 Vision 图片模块，但 PR 的 Sidecar 和 Connector 中仍保留旧的图片复制、图片保存和图片 action。

这会导致系统存在两套图片入口：

- 一套是新的 Vision 模块；
- 一套是 PR 里的旧图片逻辑。

两套逻辑可能使用不同的剪贴板、状态和失败处理，容易出现“到底是哪套代码在工作”的问题。

合并前本地版本已经把图片能力基本收束到 Vision；PR 原样合并后旧入口又回到了代码里。

### 5. 窗口固定原点的默认值和测试对不上

PR 代码默认使用一个窗口坐标策略，但 PR 自带测试仍按另一套默认值判断。

因此在没有额外环境变量时：

- 代码实际移动到一个位置；
- 测试却期待另一个位置。

原样运行会失败。不能靠下游偷偷注入环境变量掩盖，应该在 PR 内统一默认值、测试和文档。

### 6. PR 改了若干函数参数，但没有说明是否属于外部接口

PR 给多个 Sidecar 函数增加了可选参数。旧调用暂时还能运行，但没有说明：

- 哪些参数是公开接口；
- 哪些只是内部参数；
- 默认值是什么；
- 以后能不能删除；
- 返回数据有没有变化。

项目要求模块之间的接口和字段保持稳定，所以这部分必须补充合同说明和兼容测试。

### 7. OCR 改写后需要重新验证消息去重

同一条消息如果因为 OCR 排序、成员名字、气泡位置或角色标签稍有变化，就可能被当成一条新消息。

这会导致：

- 同一张图片反复触发；
- 同一句话反复进入 Brain；
- 同一个会话重复回复。

合并前已经做过一轮去重修复，但 PR 大幅改了 OCR 输出格式，必须重新验证，不能默认原去重仍然有效。

### 8. PR 的自动测试证据不够完整

PR 声称 OCR 和窗口规划测试通过，但当时没有完整的 CI 证据。原样复跑还发现了固定原点默认值矛盾。

以后需要提供：

- 固定提交号；
- 完整运行命令；
- 通过和失败数量；
- 跳过测试的原因；
- 群聊、同名会话和类型变化的截图回放。

## 这些问题和 PR 的关系

### 可以明确归因于 PR 的

- 群聊标题结构没有被利用；
- 群成员名字和正文没有正确分离；
- 会话类型被当成硬身份；
- 已打开会话可能被再次点击；
- 侧栏增强 OCR 带来的候选污染风险；
- 旧图片入口重新出现在 PR 文件中；
- fixed-origin 默认值和测试矛盾；
- PR 新增接口但没有合同说明。

### 属于 PR 和本地代码共同的接缝问题

- 多个会话互相等待，造成一个会话正常、另一个不回；
- 文字已经写入输入框，但发送没有确认；
- 连续点击、切换、复制、重试过于机械，可能触发微信掉线。

这些问题不能只修改 PR，也不能只修改本地 Scheduler。双方需要共同做多会话和真实微信测试。

### 不应归咎于 PR 的问题

- Brain 回复中出现“人工同事”等角色话术；
- 商品库字段和大风车数据；
- Vision 模型识别车型；
- 本地启动时遗留任务；
- 本地 synthetic/stale 会话记录造成的错误候选。

这些属于 Brain、商品库、Vision 或本地调度模块，不应写进 PR 的 OCR 特判。

## 建议的修复顺序

### 第一优先级：先修群聊和会话身份

1. 先看活动聊天窗口的结构，再决定是私聊还是群聊；
2. 成员数、成员名字和气泡位置属于结构证据；
3. 会话 key/title 是物理身份，类型只是可变化的属性；
4. 成员名字不能进入客户正文；
5. 已确认当前会话正确时，不再重复点击。

### 第二优先级：再修窗口动作和可靠性

1. 统一 fixed-origin 默认值、测试和文档；
2. 明确旧 key 重新绑定到新 key 的过程；
3. 把“文字写入”“发送动作”“发送成功确认”分开；
4. 重新验证 OCR 轻微变化不会重复触发；
5. 增加真实截图和真实微信回归。

### 第三优先级：清理残留和合同

1. 清理或明确禁用旧图片入口；
2. 说明新增参数是否公开；
3. 补齐 CI 和测试报告；
4. 不改变现有外部接口、字段和 Brain 回复方式。

## 不要采用的修法

- 不要写死“新数据测试”“许聪”等账号特判；
- 不要用“排除 2、3、纯数字”解决 OCR 问题；
- 不要退化成只按会话名称发送；
- 不要为了回复成功而放宽会话身份守卫；
- 不要把图片能力重新塞回 Sidecar 或 Scheduler；
- 不要让 Guard、RAG 或本地模板代替 Brain 写客户回复。

## 重新合并前必须测试

- 普通私聊；
- 真实群聊，标题带成员数；
- 侧栏先判私聊、打开后判群聊；
- 同名私聊和群聊同时存在；
- 连续追问；
- 两个会话交替来消息；
- 图片、文字、语音混合；
- 已打开会话不应被重复点击；
- 窗口失焦、登录失效、发送未确认；
- OCR 轻微抖动时不应重复触发。

每个测试都要同时证明：正确消息能被读到，错误目标不会被点击，Brain 能收到真实消息，发送目标没有串会话。
